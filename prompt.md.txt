# VAPT RECONNAISSANCE AND TLS ASSESSMENT PLATFORM
# AUTHORITATIVE IMPLEMENTATION SPECIFICATION

============================================================
IMPORTANT — READ BEFORE IMPLEMENTATION
============================================================

This project is NOT a generic URL scanner.

This project is a security-tool orchestration platform that provides a professional UI around REAL open-source security tools.

The most important requirement is:

DO NOT REIMPLEMENT THE DISCOVERY LOGIC OF THEHARVESTER.

DO NOT create a custom subdomain enumeration algorithm and assume it will reproduce theHarvester.

DO NOT generate simulated/fabricated discovery results.

Instead, integrate the actual open-source THEHARVESTER project/implementation and use its real discovery capabilities.

Likewise, use the actual TESTSSL.SH tool for TLS/SSL assessment.

The application should add value through:

- orchestration
- target validation
- scope enforcement
- result validation
- active/inactive classification
- HTTP/HTTPS probing
- result normalization
- TLS result parsing
- HTTP header analysis
- correlation
- dashboard
- findings
- reporting
- scan history
- audit logging

The external security tools remain responsible for their specialized security functionality.

============================================================
3. DO NOT REIMPLEMENT THEHARVESTER
============================================================

This is a HARD requirement.

TheHarvester is an existing open-source reconnaissance project.

The application must leverage the actual theHarvester implementation rather than attempting to recreate its functionality using custom HTTP requests, search-engine scraping, regex-based discovery, or a simplified subdomain list.

The goal is to preserve the discovery capability of the real tool.

Use the actual project as the discovery engine.

Possible integration approaches, in preferred order:

1. Programmatic/library integration if stable and supported.
2. Controlled subprocess execution of the installed theHarvester CLI.
3. Integration of a properly licensed project copy/fork when required.

Choose the most maintainable approach after inspecting the installed/current theHarvester implementation.

Do NOT arbitrarily copy individual files from the project without understanding its dependencies and license.

Preserve required open-source license/attribution information.


============================================================
4. INSPECT THEHARVESTER FIRST
============================================================

Before implementing the discovery adapter:

1. Inspect the installed theHarvester version.
2. Inspect its CLI/API capabilities.
3. Inspect its supported output formats.
4. Inspect its normalized result/evidence model.
5. Inspect how subdomains/hostnames are represented.
6. Determine the most reliable machine-readable output format.
7. Prefer structured output over parsing terminal text.

The integration must be version-aware.

Do not assume that command-line arguments or output formats are identical across versions.

The application should detect tool availability/version during startup or system health checks.


============================================================
5. THEHARVESTER ADAPTER
============================================================

Create a dedicated adapter:

TheHarvesterAdapter

Responsibilities:

- verify tool availability
- determine version
- construct safe execution arguments
- execute theHarvester
- capture output
- capture errors
- enforce timeout
- store raw evidence
- parse structured results
- return normalized discovery objects

Example conceptual interface:

TheHarvesterAdapter
    |
    +-- check_availability()
    +-- get_version()
    +-- discover(domain, options)
    +-- parse_results()
    +-- normalize_results()

The adapter must NOT contain the actual discovery intelligence.

TheHarvester remains the discovery engine.


============================================================
6. THEHARVESTER EXECUTION
============================================================

For a target:

example.com

execute the real theHarvester tool using safe process execution.

DO NOT:

- use shell=True with user-controlled input
- concatenate user input into a shell command
- execute arbitrary commands
- scrape terminal output when structured output is available

Use argument arrays.

Conceptually:

[
    "theHarvester",
    "...validated arguments..."
]

The exact command MUST be determined from the installed version's supported CLI.

The application must not assume one fixed version.

============================================================
10. SUBDOMAIN NORMALIZATION
============================================================

After receiving theHarvester results:

1. Normalize hostnames.
2. Convert to lowercase.
3. Remove unnecessary trailing dots.
4. Remove duplicate records.
5. Validate hostname syntax.
6. Validate target scope.
7. Reject malformed values.

Do not modify valid hostnames unnecessarily.

============================================================

============================================================
13. ACTIVE WEB ASSET VALIDATION
============================================================

After DNS validation:

Probe:

http://hostname
https://hostname

Capture:

URL
scheme
status code
response time
redirect location
content type
server header where available
connection error


IMPORTANT:

HTTP 403 is NOT inactive.

HTTP 401 is NOT inactive.

HTTP 404 is still evidence that a web service responded.

HTTP 500 is still evidence that a web service responded.

Examples:

200 → ACTIVE
301 → ACTIVE
302 → ACTIVE
403 → ACTIVE
404 → ACTIVE
500 → ACTIVE

Timeout/connection failure:

Potentially INACTIVE

Always preserve the actual status code and error.
